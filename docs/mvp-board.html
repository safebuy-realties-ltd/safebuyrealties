The limit was never developer-days, it is review hours, and that did not change when the week ended. A small PR costs 30 to 45 minutes to review properly and a deep-review row costs a good deal more, which is why each wave below is sized by its deep-review count and not just its story count. The original figure on this line said one reviewer could take 12 to 15 PRs a week; this repository has since merged 11 in a day, twice, so read it as a good working day rather than a weekly ceiling. The waves are also serialised by this page: every story PR has to bring the whole of it up to date in the same diff, and two PRs both moving the counter tiles conflict on purpose, so they merge one at a time with a rebase between them.

Wave 1 opens by closing the week's own worst finding: the credential that signs identity now fails closed like the other three. E5-S6 (#119) puts assertJwtSecret() in main.ts beside the database, CORS and payment guards, so production exits non-zero when JWT_SECRET is unset, empty, under 32 characters, or still the development default — before Nest is created and therefore before a single forgeable token can be signed. Three judgement calls are worth a reviewer's minute. A configured value is returned verbatim, never trimmed, so the change cannot invalidate a session already signed. The development default is now a real 45-character string that .env.example ships unchanged, which means deploying the example file is rejected by identity rather than by length — the old placeholder was 41 characters, public, and would have passed any length rule. And outside production the guard warns rather than blocks, because the secret that is set but too short is the one somebody is about to promote. Two guards were still unbuilt when this landed, for a different reason: rate limiting (E5-S1) and real sessions (E5-S5) were wave 3. Both have since merged, as #129 and #131, but only one of them changed anything a user can feel. E5-S5 ships behind a flag that has to stay off, so a stolen token is still valid for seven days with no way to revoke it, and it stays that way until the browser half exists and the flag can be turned on.

And the quieter finding, which took two words of Dockerfile and still has not reached production. E7-S6b (#120) points the container HEALTHCHECK at /api/v1/health/ready instead of /api/v1/health, and lifts --start-period from 20s to 180s. The bare endpoint answers 200 from static values and touches nothing, so a container whose database was unreachable reported itself healthy — the exact failure the readiness probe E7-S6 built on day 2 exists to make visible, and nothing was polling it. The start period matters for the opposite reason: the container runs prisma migrate deploy before Nest boots, readiness cannot pass until both finish, and 20s could mark a container unhealthy while it was still legitimately migrating. 180s is a judgement rather than a measurement — failures inside the start period do not count towards --retries, so a generous value costs only a slower verdict on a container that was never going to start. The sentence to carry out of this story is that fixing the image did not fix production. Render does not run the image's HEALTHCHECK; its check is a Health Check Path in the dashboard, there is no render.yaml here, and with no path set that check is a TCP probe against the open port — which a container with a dead database passes exactly as the old healthcheck did. docs/RUNBOOK.md §2.2 now carries Render's own table (stop routing after 15 seconds of failure, restart after 60, cancel a deploy after 15 minutes), the consequence that a restart cannot fix a dependency on a service that migrates on every start, and an open item naming the one setting. That setting is a stakeholder action, and it is the second one wave 1 has produced: this page can be right about the image while the platform ignores it.

Then the wave's first M, and the one where the privilege system started enforcing what it had only been drawing. E4-S1 (#121) declares a required privilege on every operator route and mounts PermissionsGuard on every controller that has one. Sixteen privileges existed and gated the navigation; the API checked them on two controllers and gated everything else on @Roles(STAFF, ADMIN). Since prisma/seed.ts seeds Content Manager, Operations Officer and Finance Manager all as UserRole.ADMIN, that role check admitted all three to the same endpoints — and a content manager could call POST /escrow/:id/release. The default is now deny. An operator on a route that admits operators but names no privilege is refused, so adding an endpoint and forgetting the declaration breaks it rather than publishing it, and route-inventory.ts walks the live Nest router so operator-routes.spec.ts fails the build before that can reach an environment. Three things a reviewer should press on. The fail-closed default must not deny what it should allow: a buyer, seller or professional already admitted by @Roles is passed through unmeasured, because ROLE_DEFAULT_PERMISSIONS gives them the empty set and the one route open to both audiences — a professional filing their own DD report — could not otherwise be expressed. The super admin bypass stays, because SUPER_ADMIN is the account that restores access when the privilege data itself is wrong, but it is audited on every pass now rather than only when it changed the outcome. And a matrix test drives each seeded role against each privileged route, which is what turns "the menu is hidden" into "the API refuses" — the sixth criterion, and the whole point of the story.

And wave 1 closes on the story that makes the other three legible in production. E7-S1 (#122) replaces Nest's console logger with one JSON object per line, an AsyncLocalStorage request context, a correlation id and an error tracker. Before it, a fault in production had no request identity at all: a user's report could not be tied to a line in a stream, and the three guards wave 1 built would refuse a request without leaving anything a reader could follow. Four judgement calls carry the story. The access line is written from res.on("finish") rather than an interceptor, because an interceptor never runs for a request a guard rejected — which after E4-S1 is a great many of them, and they are exactly the ones worth seeing. Caller fields are spread before the envelope so no log call can impersonate level, ts or correlationId. An inbound x-request-id is accepted but validated, since it is client-controlled text heading for a log stream and CRLF in it is header splitting. And no vendor was introduced: the story named no dependency, and picking a tracker means picking an account and a data-residency posture, which is not a developer's call to make alone — so what shipped is the part that is ours, a stable fingerprint per failure, an occurrence count so a crash loop reads as one incident, and ERROR_TRACKER_WEBHOOK_URL to point at whatever is eventually chosen. The finding inside the story is smaller and worth repeating. That fingerprint joins its parts on a NUL byte, which is the correct separator and was written as a raw byte rather than an escape; two of them were enough for git to classify the file as binary and serve Bin 6992 -> 7040 bytes in place of a diff. The code was right and unreviewable at the same time, and nothing in CI would have said so.

Wave 2's two deep-review rows each found something their titles did not promise. E2-S2 (#123) makes the Paystack webhook idempotent, and the guard it could actually ship is the service-level one: an event id is processed once per run, a stale body is rejected on signature freshness, and a duplicate credit cannot be written twice. The durable half, a ProcessedWebhookEvent row that survives a restart, needs a migration on the shared cloud database, and a migration here is a scheduled event rather than an afternoon, so that criterion is written up as waiting on a window rather than ticked. E4-S3 (#125) drives 24 resource-scoped routes against ten personas, 240 cells written out by hand rather than computed from the code under test, and the table corrected itself on its first run: it said the seller of a listing should get 403 on GET /escrow/:transactionId, and the service admits them on purpose. The finding that outlived the suite is GET /api/v1/standalone-dd/orders/:serviceId, which mounts no guard and whose service method takes no actor argument at all, so there is nothing in the request an ownership check could be written against.

And the two rows that closed wave 2 both did it by refusing to take on work they could have taken on. E7-S2b (#127) puts a bar on what a pull request adds rather than on what the repository already has. scripts/diff-coverage.mjs joins two inputs that were already being produced, the lcov each runner writes and git diff --unified=0 base...HEAD, and holds the intersection to 80 percent, so a repository sitting at 4.91 percent on the frontend is still allowed to merge and is not allowed to make it worse. It is two bars rather than one knob: 80 percent across the whole diff, plus a rule that any single changed file with ten or more new lines and none of them covered fails on its own, because an average lets one untested file hide behind four tested ones. The escape hatch is diff-coverage-exception: <reason> in the pull request body, the same shape as no-board-update:, and the reason is the price. CH-1 (#128) is the flag mechanism the rules have been quoting since day one. Eleven keys in a closed registry, every roadmap flag off by default, a gated route answering 404 rather than 403 so a feature switched off is indistinguishable from one never built, and four levels of resolution the API will tell you apart: kill switch, runtime override, FEATURE_<KEY> on Render, registry default. Two of those four survive a restart and two do not, which is why the response says so out loud. The kill switch turns things off and nothing on, on purpose, because a control that could enable would be a second enable path and the point of the story was to have one. What it does not do is fix the unowned route E4-S3 found: GET /api/v1/standalone-dd/orders/:serviceId now has a switch on it, and a switch is not an authorization check.

Wave 3 opens on the only row left that was an open door rather than a missing feature. Everything else in this wave is work that has not been built. E5-S1 (#129) was a login endpoint, a registration endpoint and a whole guest checkout taking unlimited attempts, and it shipped as two limits that count different things, neither of them a new dependency. The request throttle is a fixed window per client address mounted as the third APP_GUARD, so a route is covered by default rather than when an author remembers a decorator, with eight policies in a closed registry and each one overridable through THROTTLE_<KEY> on Render. Under it sits the tier that actually stops a password guess, because a patient attacker just slows down beneath a per-minute limit: failed logins counted per account and per source address over a rolling hour, on a ladder that lengthens as it goes, five failures buying a minute and twenty buying half an hour. That tier survives a restart and it needed no schema change to do it, which matters here more than it would elsewhere: the durable half of E2-S2 is still waiting on a migration window on the shared cloud database, and this story refused to join that queue by writing its attempts into the AuditLog table that already exists.

Three things in E5-S1 are worth a reviewer's minute, and one of them was not in the story. The lockout is checked before the user lookup, so a locked answer is byte-identical for a real account and an invented one, and what is stored is a sha256 of the email and of the address rather than either in the clear, so the table cannot be searched by email and a rejection carries the correlation id E7-S1 added and nothing else. Both tiers answer the same 429, code TOO_MANY_REQUESTS with Retry-After, set in one place, and neither says which tier refused, because a message that tells them apart is an oracle. THROTTLE_DISABLED clears an incident the request limiter caused and deliberately cannot touch the lockout, since an environment variable that could switch off account protection is the one somebody sets at 3am and never unsets. The thing that was not in the story is trust proxy, and it is the reason the rest of it works. req.ip is what the limit counts, what the lockout keys on and what four audit call sites record, and with no hop count Express reported the load balancer for every caller: the whole internet in one bucket, and the audit log recording the proxy rather than the user. It is a hop count and never true, so a client cannot choose its own bucket by writing X-Forwarded-For. TRUST_PROXY_HOPS has to be set to 1 on Render, and that is one more setting only a stakeholder can change, alongside the Render health check path wave 1 found and the migration window E2-S2 is still waiting on.

Wave 3's second row is the first story on this board that shipped switched off, and saying so plainly is half of it. E5-S5 (#131) is server-side sessions: a fifteen-minute access token beside a rotating refresh token, one family per sign-in, and only the sha256 of each refresh secret written down. Presenting a spent token revokes the whole family and writes a security alert, so a stolen refresh token is worth one request rather than a week. GET /auth/sessions lists what an account has open with device and last seen, DELETE /auth/sessions/:id ends one, and a KYC rejection or a staff deactivation ends all of them. It needed no schema change: a session family is an AuditLog row with entity = 'AuthSession', the same move E5-S1 made one PR earlier, which keeps it out of the migration queue E2-S2 is still sitting in. The flag is off and it has to stay off. Nothing in the frontend calls POST /auth/refresh; grep for it across src and there are no hits at all. Turn auth_sessions on before that client exists and every signed-in user is signed out fifteen minutes later, then again fifteen minutes after that. So the row is done and production still mints one seven-day token, exactly as it did yesterday.

Two decisions in E5-S5 are worth a reviewer's minute, and one criterion is only partly delivered. Rotation carries a ten-second leeway on purpose, because two tabs waking together present the same token and one of them loses the race, and with no window that innocent second request revokes the family and signs the person out. It is REFRESH_REUSE_LEEWAY_MS, and setting it to 0 treats every replay as reuse for anyone who wants that trade. The other decision is that the liveness check on a session id runs whether or not the flag is on, so turning the flag off does not bring back a session somebody revoked while it was live; that asymmetry is written into docs/RUNBOOK.md §11.4 along with the rest of the rollback. The criterion that is not fully met is the fourth, which asks that a password change, a password reset and a KYC rejection each end every other session. KYC rejection and staff deactivation are wired and tested. The other two are not, because this API has no password-change endpoint and no password-reset flow to hook into, and reset is E5-S3, which has not been built. The call is one line in each place once those routes exist. The story says that rather than ticking a box against code nobody has written.

Wave 3's third row is the one where the evidence found the bug and the tests did not. E8-S4 (#130) is the public web surface: robots.txt, a generated sitemap.xml, a title, description, canonical and Open Graph set per public route, RealEstateListing JSON-LD on listing detail, and noindex on every dashboard and private route in the document and in the response header both. All of it passed its unit tests, the route answered 200, the XML was well formed, and the sitemap was advertising no listings at all. SITEMAP_PAGE_SIZE was 200, ListListingsQueryDto caps pageSize at 100, so every page request was a 400, and the fetch treats a refusal as an empty catalogue on purpose. That degradation is the right behaviour and it is exactly what hid the fault. Nothing short of fetching the deployed sitemap and reconciling it line by line against the anonymous API would have said so. The constant is 100 now, its docblock names the DTO that caps it, and there are six tests for fetchSitemapListings where there had been none, led by the one that fails if anybody raises the number again.

Two findings came out of proving the rest of it, and neither of them belongs to this story. Sweeping every route the generator emits, rather than a list somebody typed, gave 37 private routes noindex in both places and 7 public routes indexable, 0 wrong. It also showed that securityHeadersMiddleware never runs on a 404 or a router redirect. That is not a development artefact: production answers /dashboard and an invented path with 404 and carries no Content-Security-Policy, no X-Frame-Options and no Referrer-Policy on either. It is pre-existing, it is wider than a metadata story, and it is written up rather than fixed inside one. The second finding is the visibility rule. Reconciling the sitemap against the API returned 7 listings, every one of them LIVE with isPublished false, and the backend calls that public while the frontend does not. Every live listing is indexed today because the backend is the side that answers, and if the frontend rule ever became the one that decided, the sitemap would empty out without a line of code changing. One setting is a stakeholder action. VITE_SITE_URL has to be set on the production Vercel project and left unset on previews, and it has to name the same origin as the backend's POA_VERIFY_BASE_URL, because a printed QR code encodes that host and a mismatch prints a dead link onto paper.

Wave 3's fourth row is the one that makes every pull request after it cheaper to review. E7-S3 (#132) inherited six end-to-end scripts in scripts/ that CI ran none of, so the only thing proving a journey still worked was somebody running it by hand against the shared cloud database. Every pull request now provisions its own Postgres as a service container, applies the committed migrations with migrate deploy, seeds it, adds the demo accounts through the API, builds the API and starts it, then runs five journeys against it: buyer on-platform purchase, seller listing to live, staff verification, standalone due diligence and guest checkout. That database lives and dies with the runner, which is criterion 1, and assertSafeDatabaseUrl() is the second lock rather than the first: outside production the API refuses to start against a non-local DATABASE_URL unless somebody sets SBR_CONFIRM_CLOUD_DATABASE_URL, and nothing in the pipeline does. Payments run mock by an explicit PAYSTACK_FORCE_MOCK=true beside NODE_ENV=test, the single combination payments-guard.ts honours, and no Paystack key of any kind is set anywhere in the workflow, so criterion 4 is answered by there being nothing left to get wrong. Two jobs rather than one, e2e-api and e2e-browser, so the browser job's Playwright download runs beside the API journeys instead of after them, and both carry timeout-minutes: 10.

Four of the five journeys were failing before this story, and not one of the four failures was environmental. Staff verification reported zero pending profiles, because listPending() filters on five conditions rather than on verifiedStatus alone: promoting a user to professional leaves a stub row already reading PENDING, with no regulatory body, no licence number and no documents, and staff never see it. The seller script now submits the licence details and uploads both documents when they are missing, and keeps its early return for an already verified profile, because upsertMyProfile resets review state on any edit and a blind PUT would un-verify the three professionals the later steps are assigned to. Guest checkout read a field called buyerId that the API has never returned, and recorded the miss as a partial reading pending until pay. Both halves were wrong: the field is buyerPublicId and it is issued when the order is created, not when it is paid, and the partial is what kept it hidden. Standalone due diligence drove staff to /login and waited twenty seconds for #email on a page that is a chooser between four portals and carries no form at all; the staff form is at /login/admin, which is where e2e-portals.mjs has always sent them. All of that is the argument for SBR_E2E_STRICT=1, which CI sets and a local run against the shared database does not: against a database seeded ninety seconds earlier, no LIVE listing to buy is a regression rather than somebody else's Tuesday. One thing this story found and did not fix, because fixing it is not end-to-end journeys in CI: backend/scripts/seed-extended-users.mjs rewrites docs/DEMO_TEST_ACCOUNTS.csv from its own list, which omits the super admin and the company account, so running it locally quietly deletes two rows from a tracked document. Gates

  • G6 escrow model confirmed against CBN and AML duties external

External inputs

  • EXT-1 production Paystack live keys and a settlement account, so real money has somewhere to land. Pairs with ADR-0002, and there is no point buying it before that decision is made
  • EXT-2 S3-compatible bucket, credentials, region decision. Pairs with ADR-0004
  • EXT-3 email domain with SPF, DKIM, DMARC, and SMTP credentials, so the product can send a message a mail server will accept. Holds 13 developer-days on its own, more than anything else here that costs only an afternoon of somebody's attention
  • EXT-4 counsel-approved PoA instrument and terms of service. Holds 1 developer-day and usually takes a fortnight to obtain
  • EXT-5 NDPR privacy notice and retention policy. Holds 6 developer-days and has the longest lead time of the seven
  • EXT-6 penetration test vendor and window. Holds 1 developer-day, and it is the booking that is missing rather than the test

A gate is a condition that has to hold before real users and real money are let near the product. An external input is something that has to be supplied from outside this repository, an account, a domain, a bucket, a published policy, a signature or a booked vendor, and no amount of engineering produces one. G4, G5 and G6 cannot be closed by writing code at all: they close when a lawyer, a security vendor and a regulator-facing adviser say so.

Words borrowed from finance, law and email

DD
Due diligence. The checks run on a property and on the person selling it before any money moves. This is the part of the product that exists today.
KYC
Know your customer. The identity check on a user before that user is allowed to move money.
PoA
Power of Attorney. The instrument a buyer signs so the platform can act on their behalf. A lawyer drafts it, not a developer.
NDPR
Nigeria Data Protection Regulation, and the Act that now carries it. It sets the privacy notice and the retention duties EXT-5 covers.
CBN
Central Bank of Nigeria. Its rules are what turn holding somebody else's money into a regulated activity rather than a feature.
AML
Anti-money-laundering. The reporting and record-keeping duties that arrive with holding client funds.
SPF, DKIM, DMARC
Three records published in a domain's DNS settings. Together they let a receiving mail server believe a message really came from that domain. Without them, transactional email is dropped or filed as spam.
SMTP
The protocol, and the credentials a mail provider issues, that let an application send email at all.
Escrow
Holding a buyer's money between payment and completion instead of passing it straight to the seller. Whether this platform does that is ADR-0002, and it is the difference between a payout form and a regulated flow.
