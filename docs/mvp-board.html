The limit was never developer-days, it is review hours, and that did not change when the week ended. A small PR costs 30 to 45 minutes to review properly, which caps one reviewer at 12 to 15 PRs a week however many agents the builder runs. The waves below are sized to that. They are also serialised by this page: every story PR has to bring the whole of it up to date in the same diff, and two PRs both moving the counter tiles conflict on purpose, so they merge one at a time with a rebase between them.

Day 3 closed in day 4. Seven PRs merged against two planned — E5-S2a (#102), the failing probe (#103), the public-asset gate on /uploads (#104), KYC and credential reads (#106), due diligence report reads (#108), plus env-file hygiene (#105) and a backlog reconcile (#107) — and at the end of all seven the day's actual deliverable was still open: E3-S1 says retire the public static route, and the route was still mounted. It came out in E3-S1d-3 (#112), two days and two sub-stories later. Seven merged PRs was not the same fact as a closed day, and this board said "done" until someone checked.

Two of those seven did less than their titles claimed. Both gaps are now closed or reduced. #105 widened backend/.gitignore only, so a root .env or .env.production stayed committable — and the root is exactly where env files are expected, since .env.example there tells you to make one and Vite reads the whole family. The one root name that was safe, .env.local, was safe by accident: it matched *.local, a Vite convention line rather than an env rule. CH-3 (#113) put the family pattern in the root file, where it covers every directory instead of one. #107's reconcile was sound, but it predated #108 and its suggested two-way split for E3-S1d has since been shown wrong — the backlog caught up in #112, and DOCS-6 (#116) has now closed that paragraph along with the rest of the sweep. Neither was a regression; both were the gap between what shipped and what the row said, which is the thing this board exists to make visible.

E3-S1 closed by deleting a route, not by adding one. What was left was not what the row said: the mount was held open by public listing imagery, the last thing on the frontend still building an /uploads/ URL. The obvious answer was a second, public delivery route beside the authorized one. E3-S1d-3 did the opposite — /api/v1/documents/file took optional authentication, so one route now decides per Document row and serves listing_hero and listing_gallery to a visitor with no session while refusing the title deed one row away. That absorbed the E3-S1b gate rather than leaving two gates on one prefix, which is how the next leak would have got in.

The coverage floor was measured, and the measurement was the finding. E7-S2 (#114) set thresholds just under today's numbers in both suites and made CI publish the reports. The backend was already measuring all 155 of its files: 41.7% of statements. The frontend was not measuring anything, and its default would have reported 48.06% — a number computed over the 20 files the tests happen to import, out of 185. Measured the way the backend measures, it is 4.91%. Both numbers are now written beside the thresholds that enforce them. The other half of the criterion, a strict bar on new and changed files, is diff coverage: no runner here can express it, so it is E7-S2b rather than a tick.

The board rule was updating three fields on a page that states everything six times. CH-5 (#115) is the answer to that. Two were sitting on this page when the check went in: the go-live tile said 2 gates wait on external input where the list marks 3, and the review queue still led with #114, which had merged. Neither would ever have been caught by a rule that stops at the row. validate:board now checks every restated number against the rows, so the table in rule 8 is enforced rather than advised.

The week discovered four stories — E5-S2a, E7-S2b, E5-S6 and E7-S6b — and half of them came out of a documentation story that shipped no code. E7-S5 (#117) is a runbook, an environment matrix and a secrets checklist, and writing the matrix meant asking of every variable what happens when it is missing. Two answers were wrong. JWT_SECRET has no boot guard: unset, the API starts and signs every session token with dev-secret-change-me, a string published in this repository, so anyone who reads it can forge a token for any user — that is E5-S6, and it is the most severe single finding of the week. And the container HEALTHCHECK polls /api/v1/health, the bare handler that returns ok without touching anything, rather than the /health/ready probe E7-S6 built on day 2 to answer that exact question — that is E7-S6b. Both were documented and filed rather than fixed inside an S-sized docs story, which is rule 5 working; both are also the argument against treating documentation as the part to skip.

What follows the week is not another week, it is three waves, and 10 startable stories are on the schedule. Twenty-nine stories remain; 19 of them sit behind a stakeholder decision, an external party or a story that does. The other 10 need nobody — 34 developer-days after E5-S6, E7-S6b and E4-S1, laid out below as Wave 1 (8 days, 5 spent), Wave 2 (12) and Wave 3 (19). The ordering is not preference. E4-S1 precedes E4-S3 because a cross-role test suite tests a guard that has to exist first; DOCS-4 is last because it freezes what the other twelve changed; and the deep-review stories — the guards, the authorization work, the session rewrite — are spread roughly half and half through each wave rather than stacked, because stacking them idles the builder behind one approver. At the end of wave 3 there is no wave 4, and that is the point: everything still standing is behind an ADR, an external input or a story that is, and the Not scheduled card below names all 19 by epic. That list is the ask, and it is the whole ask.

Wave 1 opens by closing the week's own worst finding: the credential that signs identity now fails closed like the other three. E5-S6 (#119) puts assertJwtSecret() in main.ts beside the database, CORS and payment guards, so production exits non-zero when JWT_SECRET is unset, empty, under 32 characters, or still the development default — before Nest is created and therefore before a single forgeable token can be signed. Three judgement calls are worth a reviewer's minute. A configured value is returned verbatim, never trimmed, so the change cannot invalidate a session already signed. The development default is now a real 45-character string that .env.example ships unchanged, which means deploying the example file is rejected by identity rather than by length — the old placeholder was 41 characters, public, and would have passed any length rule. And outside production the guard warns rather than blocks, because the secret that is set but too short is the one somebody is about to promote. Two guards remain unbuilt for a different reason: rate limiting (E5-S1) and real sessions (E5-S5) are wave 3, and until they land a stolen token is still valid for seven days with no way to revoke it.

And the quieter finding, which took two words of Dockerfile and still has not reached production. E7-S6b (#120) points the container HEALTHCHECK at /api/v1/health/ready instead of /api/v1/health, and lifts --start-period from 20s to 180s. The bare endpoint answers 200 from static values and touches nothing, so a container whose database was unreachable reported itself healthy — the exact failure the readiness probe E7-S6 built on day 2 exists to make visible, and nothing was polling it. The start period matters for the opposite reason: the container runs prisma migrate deploy before Nest boots, readiness cannot pass until both finish, and 20s could mark a container unhealthy while it was still legitimately migrating. 180s is a judgement rather than a measurement — failures inside the start period do not count towards --retries, so a generous value costs only a slower verdict on a container that was never going to start. The sentence to carry out of this story is that fixing the image did not fix production. Render does not run the image's HEALTHCHECK; its check is a Health Check Path in the dashboard, there is no render.yaml here, and with no path set that check is a TCP probe against the open port — which a container with a dead database passes exactly as the old healthcheck did. docs/RUNBOOK.md §2.2 now carries Render's own table (stop routing after 15 seconds of failure, restart after 60, cancel a deploy after 15 minutes), the consequence that a restart cannot fix a dependency on a service that migrates on every start, and an open item naming the one setting. That setting is a stakeholder action, and it is the second one wave 1 has produced: this page can be right about the image while the platform ignores it.

Then the wave's first M, and the one where the privilege system started enforcing what it had only been drawing. E4-S1 (#121) declares a required privilege on every operator route and mounts PermissionsGuard on every controller that has one. Sixteen privileges existed and gated the navigation; the API checked them on two controllers and gated everything else on @Roles(STAFF, ADMIN). Since prisma/seed.ts seeds Content Manager, Operations Officer and Finance Manager all as UserRole.ADMIN, that role check admitted all three to the same endpoints — and a content manager could call POST /escrow/:id/release. The default is now deny. An operator on a route that admits operators but names no privilege is refused, so adding an endpoint and forgetting the declaration breaks it rather than publishing it, and route-inventory.ts walks the live Nest router so operator-routes.spec.ts fails the build before that can reach an environment. Three things a reviewer should press on. The fail-closed default must not deny what it should allow: a buyer, seller or professional already admitted by @Roles is passed through unmeasured, because ROLE_DEFAULT_PERMISSIONS gives them the empty set and the one route open to both audiences — a professional filing their own DD report — could not otherwise be expressed. The super admin bypass stays, because SUPER_ADMIN is the account that restores access when the privilege data itself is wrong, but it is audited on every pass now rather than only when it changed the outcome. And a matrix test drives each seeded role against each privileged route, which is what turns "the menu is hidden" into "the API refuses" — the sixth criterion, and the whole point of the story.

Carry these two rules into every wave. Pass --base main on every gh pr create, and run gh pr list --json number,title,baseRefName --jq '.[] | select(.baseRefName != "main")' before reviewing — silence means every open PR targets main. That one-second check would have caught the #100 failure immediately. And every story PR brings the whole of this page up to date in the same diff — the row, its schedule card, the tiles, the header, the queue and any count the prose quotes — with npm run validate:board locally and enforced in CI, because every time this board went stale it was found by a person rather than by a check.

Agent working agreement hand this to every agent alongside the story

  1. One story, one PR, single purpose. Never combine two stories to save a round trip
  2. Copy the acceptance criteria verbatim into the PR description and tick them individually. Untickable criteria mean the story was not understood, which is a signal worth having early
  3. No story is done without pasted output from npm run validate:tsc, npm test, and cd backend && npm test
  4. Cite a file and line for every behavioural claim, matching the backlog's own standard
  5. If a story turns out bigger than its size, stop and say so rather than expanding scope
  6. Never run prisma migrate reset. The database is shared across local, preview and production
  7. If the change is user-facing and there is still no feature-flag system, say so rather than inventing one

The three launch blockers one is closed, one is narrowed, one needs a decision no wave can take

Critical

The on-platform journey does not finish

DueDiligenceService has one method, create(). Orders raised against a platform listing have no queue, no assignment, no report, no completion, so no transaction reaches DD_COMPLETE, the buyer is never offered the property purchase, escrow is never funded and the seller is never paid.

Critical

The money cannot safely move

Payouts resolve the destination from two environment variables defaulting to Paystack's test account, so every seller is paid to the same place. Refunds change a status and never call the gateway. The webhook has no replay guard. E2-S4 removed the worst of it on day 2 (#99): production refuses to start without a key. The replay guard is E2-S2, in wave 2. The destination itself is E2-S1, and it is blocked on ADR-0002.

Was critical, closed in the week

Private documents were publicly readable

Uploads were served by an unauthenticated static route, so any storage key fetched a title deed, a government ID or a KYC selfie with no session. Day 3 shipped the failing probe first (#103) so the hole was executable knowledge rather than a paragraph, and E3-S1d-3 took the static mount out on day 4 (#112). The probe stays as the regression test. What remains in E3 is durable storage and upload hardening, both behind ADR-0004.
