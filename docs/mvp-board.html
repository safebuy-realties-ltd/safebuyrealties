The limit was never developer-days, it is review hours, and that did not change when the week ended. A small PR costs 30 to 45 minutes to review properly and a deep-review row costs a good deal more, which is why each wave below is sized by its deep-review count and not just its story count. The original figure on this line said one reviewer could take 12 to 15 PRs a week; this repository has since merged 11 in a day, twice, so read it as a good working day rather than a weekly ceiling. The waves are also serialised by this page: every story PR has to bring the whole of it up to date in the same diff, and two PRs both moving the counter tiles conflict on purpose, so they merge one at a time with a rebase between them.

Two of those seven did less than their titles claimed. Both gaps are now closed or reduced. #105 widened backend/.gitignore only, so a root .env or .env.production stayed committable — and the root is exactly where env files are expected, since .env.example there tells you to make one and Vite reads the whole family. The one root name that was safe, .env.local, was safe by accident: it matched *.local, a Vite convention line rather than an env rule. CH-3 (#113) put the family pattern in the root file, where it covers every directory instead of one. #107's reconcile was sound, but it predated #108 and its suggested two-way split for E3-S1d has since been shown wrong — the backlog caught up in #112, and DOCS-6 (#116) has now closed that paragraph along with the rest of the sweep. Neither was a regression; both were the gap between what shipped and what the row said, which is the thing this board exists to make visible.

What follows the week is not another week, it is three waves, and 5 startable stories are on the schedule. Twenty-four stories remain; 19 of them sit behind a stakeholder decision, an external party or a story that does. The other 5 need nobody. That is 19 developer-days, all of it Wave 3, now that waves 1 and 2 have both closed on their estimates. The ordering is not preference. E4-S1 precedes E4-S3 because a cross-role test suite tests a guard that has to exist first; DOCS-4 is last because it freezes what the other twelve changed; and the deep-review stories, meaning the guards, the authorization work and the session rewrite, are spread roughly half and half through each wave rather than stacked, because stacking them idles the builder behind one approver. At the end of wave 3 there is no wave 4, and that is the point: everything still standing is behind an ADR, an external input or a story that is, and the Not scheduled card below names all 19 by epic. That list is the ask, and it is the whole ask.

Wave 1 opens by closing the week's own worst finding: the credential that signs identity now fails closed like the other three. E5-S6 (#119) puts assertJwtSecret() in main.ts beside the database, CORS and payment guards, so production exits non-zero when JWT_SECRET is unset, empty, under 32 characters, or still the development default — before Nest is created and therefore before a single forgeable token can be signed. Three judgement calls are worth a reviewer's minute. A configured value is returned verbatim, never trimmed, so the change cannot invalidate a session already signed. The development default is now a real 45-character string that .env.example ships unchanged, which means deploying the example file is rejected by identity rather than by length — the old placeholder was 41 characters, public, and would have passed any length rule. And outside production the guard warns rather than blocks, because the secret that is set but too short is the one somebody is about to promote. Two guards remain unbuilt for a different reason: rate limiting (E5-S1) and real sessions (E5-S5) are wave 3, and until they land a stolen token is still valid for seven days with no way to revoke it.

And the quieter finding, which took two words of Dockerfile and still has not reached production. E7-S6b (#120) points the container HEALTHCHECK at /api/v1/health/ready instead of /api/v1/health, and lifts --start-period from 20s to 180s. The bare endpoint answers 200 from static values and touches nothing, so a container whose database was unreachable reported itself healthy — the exact failure the readiness probe E7-S6 built on day 2 exists to make visible, and nothing was polling it. The start period matters for the opposite reason: the container runs prisma migrate deploy before Nest boots, readiness cannot pass until both finish, and 20s could mark a container unhealthy while it was still legitimately migrating. 180s is a judgement rather than a measurement — failures inside the start period do not count towards --retries, so a generous value costs only a slower verdict on a container that was never going to start. The sentence to carry out of this story is that fixing the image did not fix production. Render does not run the image's HEALTHCHECK; its check is a Health Check Path in the dashboard, there is no render.yaml here, and with no path set that check is a TCP probe against the open port — which a container with a dead database passes exactly as the old healthcheck did. docs/RUNBOOK.md §2.2 now carries Render's own table (stop routing after 15 seconds of failure, restart after 60, cancel a deploy after 15 minutes), the consequence that a restart cannot fix a dependency on a service that migrates on every start, and an open item naming the one setting. That setting is a stakeholder action, and it is the second one wave 1 has produced: this page can be right about the image while the platform ignores it.

Then the wave's first M, and the one where the privilege system started enforcing what it had only been drawing. E4-S1 (#121) declares a required privilege on every operator route and mounts PermissionsGuard on every controller that has one. Sixteen privileges existed and gated the navigation; the API checked them on two controllers and gated everything else on @Roles(STAFF, ADMIN). Since prisma/seed.ts seeds Content Manager, Operations Officer and Finance Manager all as UserRole.ADMIN, that role check admitted all three to the same endpoints — and a content manager could call POST /escrow/:id/release. The default is now deny. An operator on a route that admits operators but names no privilege is refused, so adding an endpoint and forgetting the declaration breaks it rather than publishing it, and route-inventory.ts walks the live Nest router so operator-routes.spec.ts fails the build before that can reach an environment. Three things a reviewer should press on. The fail-closed default must not deny what it should allow: a buyer, seller or professional already admitted by @Roles is passed through unmeasured, because ROLE_DEFAULT_PERMISSIONS gives them the empty set and the one route open to both audiences — a professional filing their own DD report — could not otherwise be expressed. The super admin bypass stays, because SUPER_ADMIN is the account that restores access when the privilege data itself is wrong, but it is audited on every pass now rather than only when it changed the outcome. And a matrix test drives each seeded role against each privileged route, which is what turns "the menu is hidden" into "the API refuses" — the sixth criterion, and the whole point of the story.

And wave 1 closes on the story that makes the other three legible in production. E7-S1 (#122) replaces Nest's console logger with one JSON object per line, an AsyncLocalStorage request context, a correlation id and an error tracker. Before it, a fault in production had no request identity at all: a user's report could not be tied to a line in a stream, and the three guards wave 1 built would refuse a request without leaving anything a reader could follow. Four judgement calls carry the story. The access line is written from res.on("finish") rather than an interceptor, because an interceptor never runs for a request a guard rejected — which after E4-S1 is a great many of them, and they are exactly the ones worth seeing. Caller fields are spread before the envelope so no log call can impersonate level, ts or correlationId. An inbound x-request-id is accepted but validated, since it is client-controlled text heading for a log stream and CRLF in it is header splitting. And no vendor was introduced: the story named no dependency, and picking a tracker means picking an account and a data-residency posture, which is not a developer's call to make alone — so what shipped is the part that is ours, a stable fingerprint per failure, an occurrence count so a crash loop reads as one incident, and ERROR_TRACKER_WEBHOOK_URL to point at whatever is eventually chosen. The finding inside the story is smaller and worth repeating. That fingerprint joins its parts on a NUL byte, which is the correct separator and was written as a raw byte rather than an escape; two of them were enough for git to classify the file as binary and serve Bin 6992 -> 7040 bytes in place of a diff. The code was right and unreviewable at the same time, and nothing in CI would have said so.

Wave 2's two deep-review rows each found something their titles did not promise. E2-S2 (#123) makes the Paystack webhook idempotent, and the guard it could actually ship is the service-level one: an event id is processed once per run, a stale body is rejected on signature freshness, and a duplicate credit cannot be written twice. The durable half, a ProcessedWebhookEvent row that survives a restart, needs a migration on the shared cloud database, and a migration here is a scheduled event rather than an afternoon, so that criterion is written up as waiting on a window rather than ticked. E4-S3 (#125) drives 24 resource-scoped routes against ten personas, 240 cells written out by hand rather than computed from the code under test, and the table corrected itself on its first run: it said the seller of a listing should get 403 on GET /escrow/:transactionId, and the service admits them on purpose. The finding that outlived the suite is GET /api/v1/standalone-dd/orders/:serviceId, which mounts no guard and whose service method takes no actor argument at all, so there is nothing in the request an ownership check could be written against.

And the two rows that closed wave 2 both did it by refusing to take on work they could have taken on. E7-S2b (#127) puts a bar on what a pull request adds rather than on what the repository already has. scripts/diff-coverage.mjs joins two inputs that were already being produced, the lcov each runner writes and git diff --unified=0 base...HEAD, and holds the intersection to 80 percent, so a repository sitting at 4.91 percent on the frontend is still allowed to merge and is not allowed to make it worse. It is two bars rather than one knob: 80 percent across the whole diff, plus a rule that any single changed file with ten or more new lines and none of them covered fails on its own, because an average lets one untested file hide behind four tested ones. The escape hatch is diff-coverage-exception: <reason> in the pull request body, the same shape as no-board-update:, and the reason is the price. CH-1 (#128) is the flag mechanism the rules have been quoting since day one. Eleven keys in a closed registry, every roadmap flag off by default, a gated route answering 404 rather than 403 so a feature switched off is indistinguishable from one never built, and four levels of resolution the API will tell you apart: kill switch, runtime override, FEATURE_<KEY> on Render, registry default. Two of those four survive a restart and two do not, which is why the response says so out loud. The kill switch turns things off and nothing on, on purpose, because a control that could enable would be a second enable path and the point of the story was to have one. What it does not do is fix the unowned route E4-S3 found: GET /api/v1/standalone-dd/orders/:serviceId now has a switch on it, and a switch is not an authorization check.

Carry these two rules into every wave. Pass --base main on every gh pr create, and run gh pr list --json number,title,baseRefName --jq '.[] | select(.baseRefName != "main")' before reviewing — silence means every open PR targets main. That one-second check would have caught the #100 failure immediately. And every story PR brings the whole of this page up to date in the same diff — the row, its schedule card, the tiles, the header, the queue and any count the prose quotes — with npm run validate:board locally and enforced in CI, because every time this board went stale it was found by a person rather than by a check.

Agent working agreement hand this to every agent alongside the story

  1. One story, one PR, single purpose. Never combine two stories to save a round trip
  2. Copy the acceptance criteria verbatim into the PR description and tick them individually. Untickable criteria mean the story was not understood, which is a signal worth having early
  3. No story is done without pasted output from npm run validate:tsc, npm test, and cd backend && npm test
  4. Cite a file and line for every behavioural claim, matching the backlog's own standard
  5. If a story turns out bigger than its size, stop and say so rather than expanding scope
  6. Never run prisma migrate reset. The database is shared across local, preview and production
  7. A user-facing change ships behind a flag, off by default: declare the key in feature-flags.constants.ts, gate the route with @RequiresFeature, gate the control with <Feature>, and name the variable that turns it on in the PR

The three launch blockers one is closed, one is narrowed, one needs a decision no wave can take

Critical

The on-platform journey does not finish

DueDiligenceService has one method, create(). Orders raised against a platform listing have no queue, no assignment, no report, no completion, so no transaction reaches DD_COMPLETE, the buyer is never offered the property purchase, escrow is never funded and the seller is never paid.

Critical

The money cannot safely move

Payouts resolve the destination from two environment variables defaulting to Paystack's test account, so every seller is paid to the same place. Refunds change a status and never call the gateway. E2-S4 removed the worst of it on day 2 (#99): production refuses to start without a key. The replay guard landed as E2-S2 in wave 2 (#123), a conditional claim on the payment row that exactly one delivery of an event can win, so a re-delivered callback cannot fire a second escrow hold. The destination itself is E2-S1, and it is blocked on ADR-0002.

Was critical, closed in the week

Private documents were publicly readable

Uploads were served by an unauthenticated static route, so any storage key fetched a title deed, a government ID or a KYC selfie with no session. Day 3 shipped the failing probe first (#103) so the hole was executable knowledge rather than a paragraph, and E3-S1d-3 took the static mount out on day 4 (#112). The probe stays as the regression test. What remains in E3 is durable storage and upload hardening, both behind ADR-0004.

Read the bars as a sizing ladder, not as a calendar. A developer-day is the unit the backlog was written in, and every merged story is subtracted at the size it was published at. That is the only way the arithmetic on this page stays checkable against the backlog's own figures, and it is why the total above is rendered from the same array the bars are. It is not a forecast of elapsed time, because one builder running many agents in parallel does not spend those days one after another, and a second developer reviewing means a finished story does not sit waiting. The evidence is this repository: 11 PRs merged into main on 31 July and 11 more on 1 August, and wave 1's four stories, 8 published developer-days between them, merged as PRs 119 to 122 inside a single afternoon. On that showing the 19 developer-days still on the schedule are nearer three or four working days than six weeks, and the 78 above is a ceiling on scope rather than on time.
